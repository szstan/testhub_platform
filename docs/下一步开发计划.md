# 下一步开发计划

## 1. 计划目标

TestHub 当前已经覆盖需求分析、测试用例、API 测试、Web UI 自动化、Android APP 自动化、性能测试、数据工厂、LLM Judge、质量智能、MCP 和统一执行治理等能力。

对于 50 人左右的公司，下一阶段不继续横向扩展所有模块，而是收敛到一条高频、可交付、可度量的主流程：

> 需求 / 版本 → 测试用例 → CI 或手工执行 → 结果导入 → 风险与缺陷 → 发布质量门禁

计划的核心目标是让研发和测试团队每天都能依赖 TestHub 判断：

- 哪些需求已经被测试覆盖；
- 哪些测试已经执行；
- 哪些失败是产品问题、环境问题还是测试问题；
- 当前版本是否满足发布条件。

## 2. 当前基础

当前代码已经具备以下可复用能力：

- 需求分析和 AI 测试用例生成；
- 测试用例、版本、评审和缺陷管理；
- API、UI、APP 和性能测试执行；
- 统一执行模型：job、attempt、step、artifact、event、retry；
- CI profile、签名 webhook、幂等事件和质量门禁；
- requirement traceability 和项目级权限隔离；
- flaky profile、风险选测、quarantine 和 QI 分析；
- 数据集、fixture、插件 manifest 和执行审计；
- LLM Judge、AI 建议审计和敏感数据脱敏；
- 前端、后端、CI、迁移和 staging 发布门禁。

下一步应优先利用这些已有能力形成闭环，减少新增平行模型和平行页面。

## 3. 开发原则

### 3.1 先做高频主流程

新功能需要直接服务于测试执行、发布判断、失败排查或需求覆盖。没有明确使用团队和使用频率的功能暂缓。

### 3.2 优先集成，不重复建设

优先接入 GitHub Actions、GitLab CI、Jenkins、Jira、JUnit、Allure、OpenAPI 等现有生态，不优先建设自有 CI、缺陷系统、完整设备云或新的结果协议。

### 3.3 规则先于 AI

质量状态、发布门禁、权限和安全判断必须由确定性规则负责。AI 用于生成、解释、聚类和提出建议，不能直接绕过审批修改生产数据。

### 3.4 每个阶段都要可发布

每个阶段都要有明确的 API、页面、测试、文档和回滚边界，完成后可以独立上线和使用。

## 4. P0：Release Quality Loop

建议优先投入 4～6 周完成这一阶段。

### 4.1 稳定测试身份

为普通测试用例增加稳定的外部引用标识，例如 `external_ref` 或 `automation_key`。

要求：

- 测试标题可以修改，不影响自动化结果关联；
- CI 结果优先按稳定引用、文件路径和 provider id 关联；
- 项目内唯一，跨项目不能发生冲突；
- 关联失败时进入待确认状态，不能静默匹配错误用例；
- 记录引用变更历史。

### 4.2 CI 结果导入

优先支持：

- JUnit XML；
- Allure 结果；
- pytest、Playwright 等常见自动化结果；
- GitHub Actions、GitLab CI、Jenkins webhook；
- 结果导入幂等和重复回放；
- 用例、版本、需求、执行 job 和 artifact 的关联。

结果状态至少区分：

- passed；
- failed；
- skipped；
- blocked；
- inconclusive；
- environment_error；
- test_error。

### 4.3 CI 触发与等待

提供简单的 REST 和 CLI 入口：

- 触发测试套件或执行 profile；
- 等待执行完成；
- 查询当前进度；
- 返回明确的 CI exit code；
- 支持 callback 和轮询两种模式；
- 支持取消和超时。

建议 CLI 结果码：

| 结果 | Exit code |
|---|---:|
| 测试通过且满足质量门禁 | 0 |
| 测试失败或质量门禁失败 | 1 |
| 环境或执行基础设施失败 | 2 |
| 测试未完整执行 | 3 |
| 参数、权限或配置错误 | 4 |

### 4.4 运行对比与发布门禁

增加两个执行运行之间的对比：

- 新增失败；
- 已修复失败；
- 持续失败；
- flaky；
- 未执行；
- 受影响需求；
- 受影响 API endpoint；
- 质量门禁变化。

发布门禁应支持：

- 必须通过的关键用例；
- 允许失败数量；
- 允许 flaky 数量；
- 关键需求覆盖率；
- API contract breaking change；
- 高风险测试必须执行；
- quarantine 用例是否允许放行。

### 4.5 P0 验收标准

- GitHub Actions 能触发 TestHub 执行；
- JUnit 或 Allure 结果能导入并幂等关联；
- 同一个 CI event 重放不会产生重复执行结果；
- 能查看本次运行与上次运行的差异；
- CI 能根据质量门禁获得稳定 exit code；
- 至少一个 staging 发布流程使用 TestHub 结果作为门禁；
- 所有新增 API、模型和任务具备权限、审计和回滚测试。

## 5. P1：Traceability & Integrations

建议在 P0 稳定后投入 3～4 周。

### 5.1 Tests as Code

支持从 GitHub 或 GitLab 仓库同步 YAML 测试定义：

- pull：Git 测试定义同步到 TestHub；
- push：TestHub 修改后提交回 Git；
- 根据稳定 `external_ref` 幂等更新；
- 记录 source repository、branch、file path 和 commit；
- 文件发生变化时使用冲突保护，禁止静默覆盖；
- 同步过程提供 preview、created、updated、skipped、warnings。

### 5.2 Jira 或单一缺陷平台集成

先选择一个主流系统完成闭环，不同时支持多个平台。

建议优先选择 Jira：

- 拉取 story、epic、bug；
- 映射为需求和缺陷；
- 测试用例与需求关联；
- 失败结果生成缺陷草稿；
- 用户确认后创建 Jira issue；
- 保存外部 key、URL、同步时间和同步状态；
- token 只写不读，支持 HTTPS 和域名校验。

### 5.3 测试迁移

增加导入预览和幂等导入，优先支持：

- TestLink XML；
- JUnit XML；
- Allure JSON；
- TestRail 或 Zephyr 常见导出格式；
- CSV/XLSX；
- 通用 JSON。

导入必须支持：

- 预览样本；
- 重复项识别；
- 稳定引用映射；
- 字段映射；
- 失败行报告；
- 可回滚或保留导入记录。

### 5.4 编辑历史

完善测试用例和关联关系的变更历史，至少包括：

- 标题和优先级；
- 前置条件、步骤和预期结果；
- 标签；
- 需求关联；
- 版本关联；
- 测试套件关联；
- 评审状态和评审意见。

## 6. P1：OpenAPI Contract Testing & Coverage

如果公司的主要产品是 API 或 SaaS，这一阶段应与 P1 集成方向并行推进。

### 6.1 OpenAPI 规格管理

- 上传和版本化 OpenAPI 文档；
- 规格 diff；
- 新增、删除和修改 endpoint 检测；
- schema 和 response code 变化检测；
- 与版本和发布关联；
- breaking change 进入 CI 质量门禁。

### 6.2 自动生成 API 测试

针对每个 endpoint 生成并执行：

- happy path；
- 必填字段缺失；
- 类型错误；
- 边界值；
- 未授权请求；
- 跨用户对象访问；
- BOLA / IDOR；
- SQL、NoSQL、命令和模板注入基础检查；
- 状态流转和依赖工作流；
- 错误响应和 response schema 校验。

生成结果必须进入统一执行模型，不能成为独立的临时 AI 结果。

### 6.3 API 覆盖率

至少提供：

- endpoint coverage；
- method coverage；
- response code coverage；
- schema field coverage；
- authentication path coverage；
- negative case coverage；
- 最近版本变化但尚未测试的 endpoint。

## 7. P1：Failure Intelligence

当前 QI 已经具备 flaky、风险和 quarantine 基础，下一步重点是把结果变得可操作。

### 7.1 失败聚类

按以下信息进行确定性聚类：

- 错误类型；
- HTTP 状态和响应摘要；
- 异常类型和堆栈；
- 测试步骤；
- 截图和日志指纹；
- 环境和设备；
- 版本和提交。

### 7.2 失败分类

区分：

- 产品缺陷；
- 测试脚本问题；
- 测试数据问题；
- 环境故障；
- 设备故障；
- flaky；
- 超时和资源不足。

### 7.3 AI 使用边界

AI 可以：

- 解释失败；
- 汇总相似失败；
- 给出可能根因；
- 建议关联缺陷；
- 建议 quarantine 或重试策略。

AI 不应直接：

- 修改生产测试用例；
- 关闭质量门禁；
- 自动创建高影响缺陷；
- 覆盖人工 quarantine 决策。

## 8. P2：APP 自动化可靠性

APP authenticated smoke 需要授权材料齐全后再推进。功能方向应集中在可靠执行和诊断，而不是继续增加大量编排节点。

建议包括：

- 测试前应用状态重置；
- 设备快照或清理策略；
- 安装、卸载和数据清理；
- logcat、截图、视频和步骤级 artifact；
- 网络 mock 或代理配置；
- 稳定 accessibility ID / resource ID 支持；
- 区分产品失败、设备失败和环境失败；
- 设备能力、健康状态和容量看板；
- 设备并行执行和公平调度；
- lease 过期、heartbeat、release 的完整审计；
- 自动重试上限和重试原因分类。

在真实设备和 fixture 授权前，不创建真实业务数据，也不扩大 APP gate 范围。

## 9. 暂缓开发的范围

对 50 人规模公司，以下内容暂不作为近期主线：

- GraphQL API；
- 自建完整 CI 系统；
- 自建 Jira 或缺陷管理系统；
- 多 Agent/Rust 执行体系；
- 自建完整设备云；
- 同时支持多个 Jira、TestRail、Zephyr、Xray 等平台；
- iOS 和跨云设备矩阵；
- 高度自主的 AI 自动修复；
- 没有明确用户和使用频率的独立 dashboard；
- 复杂的自定义报表设计器。

## 10. 推荐 90 天路线

### 第 1 阶段：Release Quality Loop

- 稳定测试引用；
- JUnit/Allure 导入；
- GitHub Actions/GitLab CI webhook；
- CI 触发、等待和 exit code；
- 运行 diff；
- 发布质量门禁。

### 第 2 阶段：Traceability & Integrations

- GitHub/GitLab Tests as Code；
- Jira 同步；
- TestLink/JUnit/Allure/CSV 导入；
- 测试用例编辑历史；
- 需求、版本、测试、执行和缺陷关联。

### 第 3 阶段：Contract & Failure Intelligence

- OpenAPI 版本管理；
- API 正负向和安全测试；
- endpoint/schema coverage；
- 失败聚类和运行对比；
- flaky 和 quarantine 建议；
- AI 根因解释和人工确认。

### 第 4 阶段：APP Reliability & AI Evaluation

- APP 状态重置和快照；
- 设备视频、logcat 和截图证据；
- 网络 mock；
- 设备容量和并行调度；
- AI golden dataset；
- 模型效果、成本、延迟和 prompt injection 评测。

## 11. 取舍决策规则

每个候选功能进入开发前，至少回答以下问题：

1. 是否每周被多个团队使用？
2. 是否直接影响发布、回归或风险判断？
3. 是否能复用现有统一执行模型？
4. 是否可以通过已有生态集成解决？
5. 是否有明确的验收指标？
6. 是否增加新的权限、审计、迁移和运维复杂度？
7. 如果不做，当前用户是否会因此无法完成核心工作？

如果前两个问题都不能回答“是”，默认暂缓。

## 12. 第一优先级结论

TestHub 下一步最应该做的是：

> **CI 触发统一执行 + JUnit/Allure 结果导入 + 稳定用例引用 + 运行对比 + 发布质量门禁。**

这条链路能直接复用现有的统一执行、CI webhook、QI、traceability、quarantine 和质量门禁能力，也最容易让 TestHub 从“功能较多的测试平台”变成“研发团队依赖的质量发布平台”。

## 13. 调研依据

本计划结合当前仓库结构和以下公开项目、issue 与技术资料整理：

- [Kiwi TCMS](https://github.com/kiwitcms/Kiwi)：成熟开源测试管理系统，强调权限、自动化插件、搜索、报告和 API。
- [Kiwi：手工与自动化实际执行类型](https://github.com/kiwitcms/Kiwi/issues/4349)：反映计划执行方式与实际执行方式需要分离。
- [Kiwi：自动化用例稳定 reference ID](https://github.com/kiwitcms/Kiwi/issues/3932)：说明自动化关联不能依赖可变标题。
- [Kiwi：测试用例编辑历史](https://github.com/kiwitcms/Kiwi/issues/4085)：说明测试资产变更审计的重要性。
- [Kiwi：大规模标签查询性能问题](https://github.com/kiwitcms/Kiwi/issues/4339)：说明规模增长后的查询和数据模型治理不能后置。
- [ThoroTest](https://github.com/ecamuto/thorotest)：展示统一运行时间线、Tests as Code、GitHub/GitLab CI、Jira、迁移导入和覆盖率的组合方向。
- [Sentinel API Testing](https://github.com/proffesor-for-testing/sentinel-api-testing)：展示 OpenAPI 驱动的正向、负向、状态流、安全和性能 Agent 方向。
- [API Automation Agent](https://github.com/TestCraft-App/api-automation-agent)：展示 OpenAPI 生成、类型安全测试、LLM 评测和 prompt injection 安全评估方向。
- [Apiome Test Management Epic](https://github.com/apiome/apiome/issues/1312)：展示测试历史、CI/CD、覆盖率、flaky 信号和统一质量 dashboard 的组合需求。
- [Fern Platform](https://github.com/guidewire-oss/fern-platform)：展示通用测试结果聚合、flaky 检测、性能趋势、失败分析和智能选测方向。
- [Android UI Testing Cookbook](https://android-ui-testing.github.io/Cookbook/practices/test_runners_review/)：总结移动端测试隔离、稳定同步、重试、录屏和失败诊断等常见痛点。
- [AWS Device Farm](https://aws.amazon.com/device-farm/)：体现设备并行、视频、日志和测试诊断在移动/Web 测试基础设施中的价值。

这些项目和 issue 用于识别行业常见问题与产品方向，不代表所有功能都适合 TestHub，也不替代当前项目的用户访谈、使用数据和商业优先级判断。
