# TestHub 未来开发计划

## 1. 目标与判断

TestHub 已经具备测试管理、API/UI/APP/性能测试、统一执行、CI 结果导入、质量智能和发布门禁等大量基础能力。下一阶段不再横向增加孤立模块，而是把这些能力收敛为研发团队可以每天依赖的 Release Quality Control Plane：

> 需求/版本 → 测试用例 → CI 或手工触发 → 统一执行 → 结果与证据 → 覆盖和失败归因 → 版本化发布门禁

当前最重要的判断是：基础模型已经存在，真正的产品缺口在于 source binding、真实 dispatch、CI 操作流、运行可观察性和发布策略证据。

本路线基于当前仓库代码和 GitHub 开源项目调研整理。 stars 只用于筛选参考项目，不作为质量证明。

### 2.2 当前部分完成和实际缺口

1. **统一执行尚未成为默认可用产品流程。** `ExecutionSourceBinding` 已有模型和 worker 侧解析，但没有项目级管理 API；`CeleryExecutionDispatcher` 和 source workers 存在，但 `EXECUTION_DISPATCH_ROUTES` 默认为空；job 创建接口仍主要记录 pending job。
2. **CI trigger 还没有完成“创建后真实 dispatch”。** CLI 有 trigger/wait/gate 命令，但 trigger 主要创建 job；用户仍需要理解内部 job/dispatch 边界。
3. **执行 readiness 不可观察。** job serializer 当前不能准确告诉用户 route、adapter 和 binding 是否可用，Task Center 仍显示大量 unsupported 状态。
4. **发布策略缺少不可变证据。** gate 可以计算，但 policy version、policy snapshot、baseline 选择原因和版本上下文仍不完整。
5. **需求 coverage 主要表示关联。** 当前 coverage 可以回答需求是否关联测试，但还不能稳定区分已执行、已通过、未执行和过期。
6. **OpenAPI coverage 尚未完全连接真实执行。** 已生成 contract cases，但 operation、case kind、external_ref 和统一 step result 之间需要统一 identity。
7. **失败结果还没有形成完整的 owner/defect 修复闭环。** QI failure review、ExecutionFailureReview 和 GitHub Issues 已有基础，但缺少跨运行 canonical cluster、负责人和修复反馈。
8. **证据仍分散在 source 模块。** Playwright trace、Allure attachment、APP report、性能 raw/report 尚未全部统一到 ExecutionArtifact/QualityEvidence 查询体验。

## 3. 开发原则

### 3.1 规则先于 AI

权限、租户隔离、source binding、状态转换、发布 gate 和数据完整性使用确定性规则。AI 只负责 draft、解释、聚类和建议，不能直接关闭 gate、修改生产用例或绕过 quarantine 审批。

### 3.2 集成优先

优先复用 GitHub Actions、GitLab CI、Jenkins、JUnit、Allure、OpenAPI、Playwright、Airtest、Locust、k6 等生态。不要建设自有 CI、完整设备云或新的结果协议。

### 3.3 每阶段可独立发布

每个阶段都必须有 API、页面、测试、审计、文档和回滚边界。新增能力必须复用现有 project scope、permission、redaction、idempotency、fail-closed 和 retention 约束。

### 3.4 先验证高频主流程

功能进入开发前必须能回答：是否每周被多个团队使用，是否直接影响发布/回归/风险判断，是否可以复用已有统一执行模型，是否有明确验收指标。

## 4. P0：Release Quality Control Plane ✅ 已完成

P0 已完成代码、迁移、后端/前端测试和 control-plane 验证。生产 route、APP 业务 gate、TLS/WSS 仍按外部边界单独处理。
建议周期：4～6 周。

### P0-1 Source binding 与真实统一 dispatch

**用户价值**

研发或测试人员可以从项目中选择一个已授权的 API/UI source，创建统一 job，看到 route/binding 是否可用，并通过 UI 或 CLI 触发真实执行。

**实现范围**

- `ExecutionSourceBinding` 项目级列表、创建、更新、禁用和 readiness API；
- typed source reference 校验，例如 `api:suite:<id>`、`ui:case:<id>`、`performance:scenario:<id>`；
- source project、unified project、metadata 和权限校验；
- 使用已有 adapter registry、`CeleryExecutionDispatcher`、`source_workers`、result event contract；
- job serializer 返回真实 `ready/unsupported` 状态；
- CLI trigger 创建 job 后默认 dispatch，保留显式 no-dispatch 选项；
- 前端 source binding 页面和 source picker；
- 缺 route、binding、source project mismatch 或 APP 未批准时继续 fail-closed。

**依赖**

现有 `ExecutionJob`、`ExecutionSourceBinding`、source contract、Celery route、项目权限、真实 source fixture。API source 优先；UI 可在同一 contract 上接入，APP/性能保持各自外部 gate。

**风险**

误启用 production route、跨项目 source 访问、重复 dispatch、late event 覆盖 final state。必须保留 idempotency、worker claim、finalizer 和 quarantine governance。

**验收指标**

- 项目成员只能管理可访问项目的 binding；
- invalid typed reference、跨项目 source 和空 source project 被拒绝；
- route 配置存在时 job readiness 为 ready，缺失时明确 unsupported；
- 一个 API source 可通过 UI/CLI 创建并 dispatch；
- 重放 idempotency key 不产生重复 job/attempt；
- 缺 route/binding 时不伪造成功结果。

### P0-2 版本化发布策略和 gate 证据

**用户价值**

发布负责人能够回答当前 gate 使用了哪条策略、哪个 baseline、哪些阈值以及为什么通过或失败。

**实现范围**

- 在 `ExecutionQualityGateEvaluation` 保存 `policy_version` 和 `policy_snapshot`；
- 根据 profile gate、request thresholds、baseline 和版本上下文生成稳定 policy fingerprint；
- API/CLI/timeline 返回 policy version、snapshot、baseline、thresholds、failures、exit code；
- 支持 report-only 与 blocking；
- 保持现有 deterministic、fail-closed 和 evaluation 幂等逻辑。

**依赖**

现有 `ExecutionProfile.quality_gate`、`run_comparison.py`、`ExecutionQualityGateEvaluation`、Version/Build/Job。

**风险**

策略 JSON 变更后历史结果不可解释、baseline 选择不一致、门禁阈值被误读。必须保存不可变 snapshot 和 evaluation audit。

**验收指标**

- 每条 gate evaluation 都可恢复 policy version/snapshot；
- 同一输入重复评估保持幂等；
- gate 失败可定位到具体指标、case 和 baseline；
- CI exit code 与最终 gate 一致。

### P0-3 控制面和 integration health

**用户价值**

用户打开执行中心即可看到最近运行、gate、关联率、unmatched、route、webhook 和 worker 健康状态，不必手工输入 job ID。

**实现范围**

- 扩展 execution metrics/control-plane API；
- 展示最近运行、最近 webhook/import、关联率、unmatched、gate pass rate、flaky 数和 route readiness；
- 改造 Task Center、Quality Loop、Traceability 页面；
- 所有列表保持分页、项目隔离和权限过滤；
- 复用 `WebhookEvent`、`ExecutionBuild`、`ExecutionJob`、step result 和现有 QI summary。

**验收指标**

- 默认页面直接展示最近运行；
- route/binding/webhook 长时间不健康时有明确状态；
- run 可以打开完整 timeline、policy 和 artifact；
- control-plane API 在目标数据量下分页且不泄露跨项目数据。

### P0-4 需求 coverage 从“已关联”升级为“已验证”

**用户价值**

发布负责人可以区分“有测试”“已执行”“已通过”和“本版本未执行”。

**实现范围**

- 复用 BusinessRequirement、RequirementTestCaseLink、ExecutionRequirementLink、Build coverage、Job 和 StepResult；
- 增加 linked/executed/passed/unexecuted/stale 摘要；
- 支持 critical requirement coverage 进入 gate；
- Traceability 页面展示 requirement → testcase → run → result → defect 链路。

**验收指标**

- coverage 不再把仅关联测试误报为已验证；
- 可按项目/版本查看未执行需求；
- critical requirement 未满足时 gate 能阻断或报告。

### P1-3 Evidence Explorer ✅ 已完成

- 性能 report、raw CSV、run log、metric snapshot。

所有 evidence 继续使用 hash、media type、size、retention、source provenance 和权限边界。

参考：[Playwright](https://github.com/microsoft/playwright)、[Allure](https://github.com/allure-framework/allure2)、[Airtest](https://github.com/AirtestProject/Airtest)。

### P1-4 性能质量进入统一 release gate ✅ 已完成

- 将 p95/p99、error rate、TPS、duration、CPU 等指标映射到统一 gate；
- 复用现有 SLA、baseline、comparison 和 unified completion callback；
- 按版本、环境和 scenario 选择 baseline；
- 将性能 regression 展示在统一 run history 和 QI trend 中；
- 不建设新的压测引擎。

参考：[k6](https://github.com/grafana/k6)、[Locust](https://github.com/locustio/locust)。

### P1-5 通知和运行责任 ✅ 已完成

- gate 失败通知版本负责人；
- integration health 连续失败通知维护者；
- flaky/quarantine 到期通知 owner；
- failure cluster 重现通知责任人；
- 通知内容带 project、version、run、case、gate 和 evidence 链接。

## 6. P2：规模化和外部条件具备后的能力

### P2-0 数据规模与 Retention 治理 ✅ 已完成

已完成规模控制面、retention warning、只读 `quality_scale_report`、artifact/step/QI evidence/failure 查询索引和结果 metadata 与 artifact 内容分离的保留边界。

触发阈值默认包括：

- execution jobs：100,000；
- execution artifacts：100,000；
- artifact bytes：100 GB；
- QI runs：100,000；
- QI evidence：250,000。

规模报告默认只读；过期 artifact 清理仍要求显式批准和 `cleanup_execution_artifacts --apply`，本次没有增加自动删除或对象存储迁移。

### P2-1 APP 可靠性和容量

外部材料齐全后推进：APK/session、disposable fixture、设备能力、容量、网络和报告保留。范围包括应用清理、安装卸载、logcat/截图/视频、设备健康、lease heartbeat/release、分片调度和失败分类。

参考：[Airtest](https://github.com/AirtestProject/Airtest)。不建设完整自有 device cloud。

### P2-2 AI 诊断和智能选测

- failure summary、相似失败、变更影响、风险选测和 contract case 建议；
- 建立 golden dataset，评估准确率、误报率、延迟、成本和 prompt injection；
- AI 不直接修改生产用例、关闭 gate 或创建高影响缺陷。

### P2-3 大规模数据与 artifact 治理

- run/step/failure/artifact/source key 组合索引；
- 全部历史分页；
- result retention 与 artifact retention 分离；
- 对象存储和异步聚合；
- 记录导入和查询耗时。

参考：[Kiwi 大规模标签查询问题](https://github.com/kiwitcms/Kiwi/issues/4339)。

### P2-4 按需求增加外部连接器

只有确认使用场景后增加 Jira、TestLink、TestRail、Zephyr、Xray 等连接器。当前优先完善 GitHub Issues 和 GitHub/GitLab Tests as Code。

## 7. 暂缓范围

- GraphQL API；
- 自建完整 CI；
- 自建 Jira 或缺陷系统；
- 多 Agent/Rust 执行体系；
- 完整设备云；
- 同时维护多个外部测试管理 connector；
- iOS 和跨云设备矩阵；
- 高度自主的 AI 自动修复；
- 没有明确用户和使用频率的独立 dashboard；
- 复杂报表设计器。

## 8. 外部 gate 和发布边界

以下事项不能被普通功能开发宣称为已完成：

- APP 业务 APK、认证 session、fixture ID 和真实业务数据授权；
- 真实设备能力、容量、网络和并行执行环境；
- 正式域名、DNS、TLS 证书链、私钥交付、443、防火墙、代理和 rollback window；
- Celery worker、Redis/broker、source project binding 和 production `EXECUTION_DISPATCH_ROUTES` 配置；
- Jira 等外部系统凭证、网络出口和供应商选择。

没有这些材料时保持 fail-closed，继续使用 HTTP/WS staging 和空 route 配置，不使用自签证书替代正式 TLS gate。
