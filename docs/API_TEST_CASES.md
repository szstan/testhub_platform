# 接口测试用例与混合测试套件

接口测试模块现在支持独立的 HTTP 测试用例。一个用例引用当前 API 项目中的已保存请求，按顺序执行多个步骤，可设置每步参数、断言与响应变量提取。请求定义、用例、套件成员和执行历史分别管理。

## 从哪里开始

- 在「接口测试 → 测试用例」管理用例，支持按项目、关键词、优先级和状态筛选、分页、复制与删除。
- 在接口测试 Dashboard 点击「测试用例」指标或快捷操作进入列表，点击「编写用例」创建用例。
- 在「接口管理」打开一个已保存到当前项目集合中的 HTTP 请求，点击「创建测试用例」，进入预填首个步骤的编写页面。来源是服务端保存的请求；先保存接口编辑，再使用此入口。
- 在「自动化测试」把独立用例和原有请求加入同一个测试套件。

WebSocket 请求不作为 HTTP 用例步骤。Pre-request Script 和 Tests 中保存的 JavaScript 不会执行；可执行检查应配置为结构化断言，跨步骤传值应使用变量提取器。

## 编写和保存

填写 API 项目、名称、描述、前置条件、预期结果、优先级、状态、标签和初始变量。草稿允许先保存基本信息，实际执行至少需要一个启用的步骤。一个用例最多包含 50 个步骤，步骤只能引用同一 API 项目下的 HTTP 请求。

每个步骤可修改名称、启用状态、顺序、请求覆盖、断言和提取器。切换 API 项目时，页面会提示清除当前步骤。保存一次提交用例和全部步骤；后端在同一事务中替换步骤，无效数据不会只保存其中一部分。

步骤引用请求模板，因此后续请求定义更新会影响下一次运行。已受理的独立用例会在 worker 发送 HTTP 前核对提交时的执行配置；排队期间若用例、引用请求或环境发生变化，本次执行明确失败，不会改用新配置。核对通过后，本次执行使用已冻结的输入。参数覆盖只作用于当前步骤执行，不回写原请求；运行变量和提取变量不会回写环境或用例变量。

参数和请求头覆盖填写 JSON 对象，与模板中相应字段合并，同名字段以步骤值为准。例如：

```json
{
  "reference": "{{receipt}}",
  "page": "1"
}
```

请求体覆盖替换模板请求体。省略 `body` 字段会继承模板；显式填写 `{}` 或 `null` 会清空模板请求体。也可用以下类型化值明确表示无请求体：

```json
{"type": "none", "data": null}
```

JSON 请求体可填写普通 JSON，或使用与接口管理相同的结构：

```json
{"type": "json", "data": {"reference": "{{receipt}}"}}
```

同时支持 `raw`、`form-data`、`x-www-form-urlencoded`。请求体只随 POST、PUT、PATCH 发送。运行时未能解析的 `{{变量}}` 或 `${变量}` 会阻止该请求发送。

「关联通用测试用例」通过显式 `linked_testcase` 关联当前用户可访问的通用用例。API 项目与通用项目使用不同的数据模型，不能根据数字 ID 相同推断它们是同一个项目。

## 断言、提取与变量

步骤的 `assertions` 有三种明确含义：

| 保存值 | 执行行为 |
| --- | --- |
| `null` | 继承已保存请求中的断言 |
| `[]` | 覆盖为不配置断言 |
| 非空数组 | 用步骤断言替换请求断言 |

断言编辑器支持状态码、响应时间、响应包含、JSONPath、响应头和响应文本相等。响应时间单位为毫秒。JSONPath 期望值可填写 JSON 布尔值、数字、数组、对象或 `null`；文本可以直接填写，也可加双引号。JSONPath 使用首个匹配结果，路径缺失始终失败，存在的 JSON `null` 才能与 `null` 匹配。对象按内容比较，忽略键顺序。

新建或编辑的 JSONPath 断言使用 `comparison: "json"` 保留类型，例如字符串 `"1"` 不等于数字 `1`。未标记的旧请求断言保留原有的标量文本比较；需要显式旧行为时可使用 `comparison: "legacy"`。

HTTP 4xx/5xx 响应仍会执行断言和提取。例如预期状态码为 401 的负向用例可以通过。请求成功发送且所有配置断言通过，步骤才算通过；未配置状态码断言时，HTTP 状态码本身不会自动判失败。

提取器填写 JSON 数组。例如从首步 JSON 响应提取 `receipt`，并要求结果存在：

```json
[
  {
    "name": "receipt",
    "source": "json_path",
    "expression": "$.data.receipt",
    "required": true
  },
  {
    "name": "revision",
    "source": "header",
    "expression": "X-Revision",
    "required": false
  }
]
```

`source` 支持 `json_path` 和 `header`，响应头名称不区分大小写。同一步内变量名不能重复。提取在该步断言通过后进行；后续步骤通过 `{{receipt}}` 使用结果。必需变量缺失或提取表达式失败会使该步失败；可选变量缺失时不覆盖已有值。JSON `null` 按缺失提取值处理。

变量覆盖优先级从低到高为：

1. 执行环境变量。
2. 用例初始变量。
3. 本次执行提交的 `variables`。
4. 前序步骤已成功提取的变量。

开启「步骤失败后停止」时，失败后的步骤显示为跳过；关闭后继续执行后续步骤。禁用步骤始终跳过。不同用例的提取变量相互隔离，套件中的原有请求不会继承另一个用例提取的值。

## 后台执行和历史

先保存编辑内容，再点击「执行用例」。执行使用服务端已保存的用例；存在未保存修改时，执行按钮不可用。运行面板轮询执行记录，显示等待中、执行中、完成或失败，以及每步耗时、断言、已脱敏响应快照和提取变量名称。关闭面板会停止页面轮询，后台任务继续运行。轮询达到上限后可从「执行历史」查看最新状态。

独立用例通过 Celery 后台执行，需要可用的 broker 和 worker。使用项目配置启动 worker，例如：

```bash
celery -A backend worker -l info
```

开发环境可按操作系统选择合适的 worker pool。独立用例任务使用默认 Celery 队列；worker 必须加载 `apps.api_testing.case_tasks.execute_api_case_execution`。测试配置的 eager 模式只用于隔离验证，不能替代正式环境的队列和 worker。

执行提交返回 `202` 和持久化执行记录。broker 提交失败时返回 `503`，同时把执行记录标为失败，历史中保留错误。worker 在步骤开始时更新心跳；读取用例历史或执行详情时会回收当前用户可见项目中过期的等待/运行记录，标为失败且不重放 HTTP。超时默认 300 秒，可用 Django 设置 `API_CASE_EXECUTION_STALE_AFTER_SECONDS` 调整（最小 30 秒）；配置时应考虑正常队列等待时间。已被回收的记录不会被延迟到达的 worker 改回成功。

客户端可提交最多 128 字符的 `idempotency_key`。同一项目、同一执行用户下，相同键、相同用例、相同环境/变量及相同执行配置返回已有执行；相同键对应不同参数、用例或配置时返回 `409`。用例详情和列表包含 `execution_fingerprint`，客户端可在提交时传回该指纹；若配置已变化，服务端返回 `409` 并要求刷新。指纹不会包含配置明文，读取指纹也不会执行动态函数。请求超时后先检查执行历史；重试同一提交可复用原幂等键。页面按用例和执行配置分别保留状态不明的键，运行其他用例不会清除它们；保存了新版本后，为下一次运行生成新键。明确的 4xx 校验或权限拒绝直接显示错误，不提示「可能已开始」；传输超时或状态不明时保留原键并引导查看历史。worker 对已经离开 `PENDING` 的记录不重复发送 HTTP 请求。

历史保存脱敏结果，不保存完整原始响应对象或提取值集合。用例及混合套件中的旧请求都会在截断或写入历史之前，擦除环境和本次运行变量的值，包括在普通字段中的回显。运行所需变量会通过任务消息交给 worker；已保存的初始变量和环境配置仍属于配置数据。步骤失败、断言失败、队列故障都有独立结果，不能仅按 HTTP 提交成功判断测试通过。

有排队或运行中任务的用例暂不能编辑或删除；用例所属套件正在运行时也不能编辑。已加入套件的用例必须先移除套件关联才能删除。删除用例后，已完成历史保留用例名称快照。

## 混合套件

「自动化测试」支持按项目创建、编辑、复制和删除套件，并添加「接口用例」或「原有请求」。同一套件中的两类成员共用执行顺序，可启用、禁用、上移、下移和移除。

原有请求成员的「编辑断言」会实际保存套件级断言。套件级断言追加到请求本身的断言之后，不修改请求定义。用例成员使用用例自己的逐步断言。

混合排序和关联行操作采用不同 ID：

| 操作 | ID 含义 |
| --- | --- |
| `add-requests` / `add-cases` | 请求 ID / 用例 ID |
| `reorder` 中 `{kind, id}` | 请求 ID / 用例 ID，必须提交两类全部成员 |
| PATCH / DELETE `test-suite-requests/{id}` | 请求与套件的关联行 ID |
| PATCH / DELETE `test-suite-cases/{id}` | 用例与套件的关联行 ID |

套件正在执行时禁止修改成员、断言或排序。套件完成状态和统一执行任务的通过状态都会考虑断言结果，不能把「请求发送成功」当作「测试通过」。旧请求套件、定时任务、统一执行入口和 OpenAPI 契约工作流继续使用各自原有入口。

## API 摘要

以下路径均以 `/api/api-testing/` 为前缀，要求已登录并有对应项目权限：

| 方法与路径 | 作用 |
| --- | --- |
| GET / POST `test-cases/` | 分页查询 / 创建 |
| GET / PATCH / PUT / DELETE `test-cases/{id}/` | 查看 / 更新 / 删除 |
| POST `test-cases/{id}/duplicate/` | 复制为草稿 |
| POST `test-cases/{id}/execute/` | 后台执行，支持 `environment_id`、`variables`、`idempotency_key`、`execution_fingerprint` |
| GET `test-cases/{id}/executions/` | 此用例的分页执行历史 |
| GET `case-executions/{id}/` | 读取执行状态和脱敏结果 |
| POST `test-suites/{id}/add-cases/` | 添加同项目用例，字段 `case_ids` |
| POST `test-suites/{id}/reorder/` | 原子更新混合成员全量顺序，字段 `items` |
| GET / PATCH / DELETE `test-suite-cases/{id}/` | 查看或修改用例成员的顺序、启用状态 / 移除成员 |

用例列表支持 `project`、`status`、`priority`、`search`（或 `q`）、`page` 和 `page_size`。分页默认为 20，最大页大小为 100。权限覆盖 API 项目所有者、成员和管理员；本地环境必须属于用例的 API 项目，全局环境按其所有者或管理员权限使用。

## 数据迁移与兼容

部署代码后按项目流程执行 `python manage.py migrate`。`api_testing/0005_api_test_cases` 新增用例、步骤、执行和套件用例关联表，显式依赖通用用例迁移，不改造旧请求或旧套件数据。`0006_api_case_execution_heartbeat` 补充执行心跳字段及索引，必须与使用心跳的代码一同迁移。回退 `0005` 会删除新增表中的用例及历史，应按正常数据库变更流程保留所需数据。

原有请求被步骤引用时，删除请求或其集合/项目返回冲突，避免静默破坏用例。跨项目移动也会检查步骤和套件引用。用例信息与执行状态采用事务和运行态校验，HTTP 请求仍通过共享的出站 URL 校验与受控传输路径。

相关回归命令：

```bash
python -m pytest apps/api_testing apps/executions/tests/test_source_boundary_integrity.py -q --create-db
npm --prefix frontend run test:api-cases
npm --prefix frontend run test:interface-management-pagination
npm --prefix frontend run lint:api-cases
npm --prefix frontend run build
```
